Практическое руководство

У меня старый PHP — что делать

Если ваша ветка ещё поддерживается, обновитесь до 8.5.12, 8.4.27, 8.3.36 или 8.2.35. Если вы залочены на 8.1, 8.0 или 7.x, официального релиза PHP для них нет — но пакеты deb.sury.org содержат бэкпорт, а Ubuntu 22.04 закрыла php8.1 обычным обновлением. Сначала проверьте версию пакета: возможно, фикс уже установлен.

Дата проверки фактов: 23 октября 2026 г.

Проверить сервер

Короткий ответ

Обновите PHP до исправленной версии своей ветки. Если обновление невозможно, поставьте пакет с бэкпортом из репозитория дистрибутива или deb.sury.org. Отключение проверок безопасности и случайные PPA проблему не решают.

Ветки 8.2–8.5 получают официальные релизы PHP. Для 8.1, 8.0, 7.x и 5.x официальных релизов нет, но бэкпорты выпускают дистрибутивы и Sury. Ниже — как проверить, что именно установлено, и что делать в каждом случае.

Сценарий 1. PHP можно обновить

Это лучший путь: официальный релиз содержит все исправления ветки, а не только патч для двух CVE.

  1. Узнайте ветку и точную версию: php -v и php-fpm -v. Если команды нет, найдите версию в панели хостинга.
  2. Обновите пакеты дистрибутива: sudo apt update && sudo apt upgrade в Debian/Ubuntu или sudo dnf upgrade в RHEL-совместимых системах.
  3. Перезапустите PHP-FPM и веб-сервер: sudo systemctl restart php8.3-fpm. Без перезапуска часть воркеров останется на старом коде.
  4. Проверьте, что php -v показывает 8.5.12, 8.4.27, 8.3.36 или 8.2.35 для вашей ветки или новее.
php -v
php-fpm -v

sudo apt update
sudo apt upgrade

sudo systemctl restart php8.3-fpm

dpkg -l | grep php

Смотрите не только заголовок X-Powered-By: версия в нём может отставать от патча. Проверьте пакет: dpkg -l | grep php в Debian/Ubuntu или rpm -q --changelog php-cli | head -40 в RHEL.

Если apt upgrade не предлагает обновление, проверьте, включён ли репозиторий безопасности дистрибутива.

Сценарий 2. Вы залочены на 8.1, 8.0 или 7.x

Официального релиза PHP для этих веток нет. Патч можно получить из пакета дистрибутива или из стороннего репозитория Sury. Это не официальный канал безопасности Debian/Ubuntu: сначала проверьте, нет ли фикса в вашем дистрибутиве.

Sury — сторонний репозиторий, а не официальный канал безопасности. Сделайте снимок или бэкап, протестируйте обновление на staging и не подключайте случайные PPA.

Как подключить репозиторий Sury

Установите ключ и подключите репозиторий командами из официального README Sury:

sudo apt-get update
sudo apt-get -y install lsb-release ca-certificates curl
sudo curl -sSLo /tmp/debsuryorg-archive-keyring.deb https://packages.sury.org/debsuryorg-archive-keyring.deb
sudo dpkg -i /tmp/debsuryorg-archive-keyring.deb
sudo sh -c 'echo "deb [signed-by=/usr/share/keyrings/debsuryorg-archive-keyring.gpg] https://packages.sury.org/php/ $(lsb_release -sc) main" > /etc/apt/sources.list.d/php.list'
sudo apt-get update

Обновите только пакеты своей ветки. Пример для PHP 8.1:

sudo apt-get install --only-upgrade php8.1-cli php8.1-fpm php8.1-common

Замените 8.1 на 8.0, 7.4 или другую ветку. --only-upgrade обновляет уже установленные пакеты и не тянет лишние расширения.

Проверьте версию PHP, FPM и пакета:

php -v
php-fpm8.1 -v
dpkg -l | grep '^ii  php8.1'

Перезапустите FPM и веб-сервер:

sudo systemctl restart php8.1-fpm
sudo systemctl restart apache2

Для nginx перезапустите nginx. Если на сервере несколько версий PHP, перезапустите сервис и пул нужной ветки.

Сценарий 3. Managed-хостинг или нет root

Обновление делает провайдер. Напишите в поддержку и попросите подтвердить версию пакета, а не только версию в панели.

Что проверить в панели

  • Доступен ли выбор PHP 8.2, 8.3, 8.4 или 8.5.
  • Дата последнего обновления PHP и наличие бэкпорта для вашей ветки.
  • Перезапускаются ли воркеры PHP-FPM после смены версии.
  • Можно ли поднять staging-копию и проверить сайт до переключения.

Шаблон обращения в поддержку

Здравствуйте!

На моём тарифе используется PHP [версия]. Проверьте, пожалуйста, закрыты ли в установленном пакете CVE-2026-109618 и CVE-2026-109619.

Если исправленная версия недоступна, можно ли переключить сайт на PHP 8.2 или новее либо установить пакет с бэкпортом? Если нет, какие временные меры вы поддерживаете?

Пришлите, пожалуйста, вывод php -v и версию пакета (dpkg -l | grep php или rpm -q php-cli), а также дату последнего обновления PHP.

Спасибо.

Не отправляйте пароли, токены и данные клиентов. Достаточно версии PHP, названия тарифа и вывода php -v.

Если провайдер не может обновить PHP, единственный надёжный путь — перенос на площадку с поддерживаемой версией.

Сценарий 4. Проверьте результат заново

После обновления и перезапуска вернитесь на главную и повторите пассивную проверку. Она покажет раскрытую версию PHP, но не докажет, что патч установлен: вердикт остаётся оценкой риска.

Открыть проверку

Для автоматизации: POST /api/check с телом {"url":"https://example.com","lang":"ru"}. Описание API — в llms-full.txt.

Чек-лист после обновления

  • php -v и php-fpm -v показывают новую версию.
  • dpkg -l | grep php (или rpm -q php-cli) показывает исправленный пакет.
  • Сервис PHP-FPM и веб-сервер перезапущены.
  • Повторная проверка не показывает vulnerable или likely_vulnerable.

Чего НЕ делать

  • Не отключайте проверки безопасности, WAF, open_basedir и другие защиты ради совместимости со старым кодом. Это повышает риск, но не закрывает CVE.
  • Не ставьте PHP из случайных PPA и сборок с форумов: проверить наличие патча в таком пакете нельзя.
  • Не считайте, что смена версии в панели сразу перезапускает все воркеры. Проверьте php -v и перезапустите FPM.
  • Не оставляйте phpinfo и диагностические страницы открытыми, пока обновление не установлено.
  • Не откладывайте переход с 5.x и 7.x: бэкпорт закрывает эти две CVE, но не делает ветку поддерживаемой.

Частые вопросы о старом PHP

Мой PHP 8.1. Официального фикса правда нет?

Да, upstream-релиза PHP для 8.1 нет. Но Ubuntu 22.04 и Sury выпустили пакеты с бэкпортом: проверьте версию пакета, а не только версию PHP.

Можно ли просто обновить PHP до 8.5?

Да, если приложение совместимо. 8.5 — самая новая ветка, но сначала проверьте расширения и тесты на staging.

Безопасно ли использовать deb.sury.org?

Это популярный сторонний репозиторий, но не официальный канал безопасности Debian/Ubuntu. Подключайте его только по официальному README, с бэкапом и проверкой changelog.

Как понять, что патч уже установлен?

Посмотрите версию пакета и changelog: dpkg -l | grep php и apt-get changelog php8.1. Версия в заголовке X-Powered-By может быть старой.

Нужно ли перезапускать сервер после обновления?

Да. Перезапустите PHP-FPM и веб-сервер, иначе часть воркеров останется на старом коде.

Сработает ли проверка, если PHP скрыт?

Нет. Вердикт будет unknown: проверьте версию на сервере командой php -v.

Что делать, если хостинг не обновляет PHP?

Напишите провайдеру по шаблону выше и попросите версию пакета. Если фикса нет, переносите сайт на площадку с PHP 8.2 или новее.

Можно ли обойтись временными мерами?

Они снижают риск, но не заменяют патч. Отключение session.upload_progress и лимиты запросов не закрывают CVE полностью.

Это применимо к PHP 5.6?

Sury пересобрал и 5.6 с бэкпортом, но ветка давно не поддерживается. Для продакшена нужен переход на 8.2 или новее.

Где первоисточники?

Ссылки на Debian Security Tracker, USN-8948-1 и changelog Sury — в разделе «Источники» внизу страницы.

Источники и проверка фактов

Версии и даты сверены с первоисточниками. Если пакет обновили после публикации, ориентируйтесь на его changelog.
