Practical guide

I’m stuck on old PHP — what should I do?

If your branch is still supported, upgrade to 8.5.12, 8.4.27, 8.3.36 or 8.2.35. If you are stuck on 8.1, 8.0 or 7.x, upstream PHP has no release for you — but deb.sury.org packages contain the backport, and Ubuntu 22.04 fixed php8.1 with a regular update. Check the package version first: the fix may already be installed.

Facts checked against primary sources on October 23, 2026.

Check the server

Short answer

Upgrade PHP to the fixed release for your branch. If you cannot upgrade, install a backported package from your distribution or deb.sury.org. Disabling security checks and random PPAs do not solve the problem.

Branches 8.2–8.5 get official PHP releases. There are no official releases for 8.1, 8.0, 7.x and 5.x, but distributions and Sury publish backports. Below: how to check what is installed and what to do in each case.

Scenario 1. You can upgrade PHP

This is the best path: an official release contains all fixes for the branch, not only the patch for these two CVEs.

  1. Find the branch and exact version: php -v and php-fpm -v. If the commands are missing, check the hosting panel.
  2. Upgrade the distribution packages: sudo apt update && sudo apt upgrade on Debian/Ubuntu or sudo dnf upgrade on RHEL-compatible systems.
  3. Restart PHP-FPM and the web server: sudo systemctl restart php8.3-fpm. Without a restart, some workers keep the old code.
  4. Make sure php -v shows 8.5.12, 8.4.27, 8.3.36 or 8.2.35 for your branch, or newer.
php -v
php-fpm -v

sudo apt update
sudo apt upgrade

sudo systemctl restart php8.3-fpm

dpkg -l | grep php

Do not rely on the X-Powered-By header alone: its version can lag behind the patch. Check the package: dpkg -l | grep php on Debian/Ubuntu or rpm -q --changelog php-cli | head -40 on RHEL.

If apt upgrade offers nothing, make sure the distribution security repository is enabled.

Scenario 2. You are locked to 8.1, 8.0 or 7.x

There is no official PHP release for these branches. You can get the patch from a distribution package or from the third-party Sury repository. Sury is not the official Debian/Ubuntu security channel: first check whether your distribution already has the fix.

Sury is a third-party repository, not an official security channel. Take a snapshot or backup, test the upgrade on staging, and do not add random PPAs.

How to add the Sury repository

Install the key and add the repository with the commands from the official Sury README:

sudo apt-get update
sudo apt-get -y install lsb-release ca-certificates curl
sudo curl -sSLo /tmp/debsuryorg-archive-keyring.deb https://packages.sury.org/debsuryorg-archive-keyring.deb
sudo dpkg -i /tmp/debsuryorg-archive-keyring.deb
sudo sh -c 'echo "deb [signed-by=/usr/share/keyrings/debsuryorg-archive-keyring.gpg] https://packages.sury.org/php/ $(lsb_release -sc) main" > /etc/apt/sources.list.d/php.list'
sudo apt-get update

Upgrade only the packages of your branch. Example for PHP 8.1:

sudo apt-get install --only-upgrade php8.1-cli php8.1-fpm php8.1-common

Replace 8.1 with 8.0, 7.4 or another branch. --only-upgrade upgrades installed packages and does not pull extra extensions.

Check the PHP, FPM and package versions:

php -v
php-fpm8.1 -v
dpkg -l | grep '^ii  php8.1'

Restart FPM and the web server:

sudo systemctl restart php8.1-fpm
sudo systemctl restart apache2

For nginx, restart nginx. If the server runs several PHP versions, restart the service and pool of the branch you changed.

Scenario 3. Managed hosting or no root access

The provider performs the upgrade. Ask support to confirm the package version, not only the version shown in the panel.

What to check in the panel

  • Whether PHP 8.2, 8.3, 8.4 or 8.5 is available.
  • The date of the last PHP update and whether your branch has a backport.
  • Whether PHP-FPM workers restart after a version change.
  • Whether you can run a staging copy and test the site before switching.

Message template for support

Hello,

My hosting plan uses PHP [version]. Please confirm whether CVE-2026-109618 and CVE-2026-109619 are fixed in the installed PHP package.

If the fixed version is not available, can you switch the site to PHP 8.2 or newer, or install a backported package? If not, which temporary mitigations do you support?

Please send the output of php -v and the package version (dpkg -l | grep php or rpm -q php-cli), plus the date of the last PHP update.

Thank you.

Do not send passwords, tokens or customer data. The PHP version, plan name and php -v output are enough.

If the provider cannot upgrade PHP, the only reliable path is to move the site to a platform with a supported version.

Scenario 4. Check the result again

After the upgrade and restart, return to the main page and run the passive check again. It shows the disclosed PHP version but does not prove that the patch is installed: the verdict remains a risk estimate.

Post-upgrade checklist

  • php -v and php-fpm -v show the new version.
  • dpkg -l | grep php (or rpm -q php-cli) shows the fixed package.
  • The PHP-FPM service and the web server were restarted.
  • The new check does not show vulnerable or likely_vulnerable.

What NOT to do

  • Do not disable security checks, a WAF, open_basedir or other protections for compatibility with old code. That raises risk and does not close the CVE.
  • Do not install PHP from random PPAs or forum builds: you cannot verify that the package contains the patch.
  • Do not assume that changing the version in a panel restarts every worker. Check php -v and restart FPM.
  • Do not leave phpinfo or diagnostic pages public until the update is installed.
  • Do not postpone moving off 5.x and 7.x: the backport closes these two CVEs but does not make the branch supported.

Frequently asked questions about old PHP

My PHP is 8.1. Is it true that there is no official fix?

Yes, there is no upstream PHP release for 8.1. But Ubuntu 22.04 and Sury published backported packages: check the package version, not only the PHP version.

Can I just upgrade PHP to 8.5?

Yes, if the application is compatible. 8.5 is the newest branch, but test extensions and the site on staging first.

Is deb.sury.org safe to use?

It is a popular third-party repository, but not the official Debian/Ubuntu security channel. Add it only from the official README, with a backup and a changelog check.

How do I know the patch is already installed?

Check the package version and changelog: dpkg -l | grep php and apt-get changelog php8.1. The X-Powered-By header version can be old.

Do I need to restart the server after the update?

Yes. Restart PHP-FPM and the web server, otherwise some workers keep the old code.

Does the check work if PHP is hidden?

No. The verdict will be unknown: check the version on the server with php -v.

What if my hosting provider does not update PHP?

Send the template above and ask for the package version. If there is no fix, move the site to a platform with PHP 8.2 or newer.

Are temporary mitigations enough?

They reduce risk but do not replace the patch. Disabling session.upload_progress and request limits do not fully close the CVE.

Does this apply to PHP 5.6?

Sury also rebuilt 5.6 with the backport, but the branch has been unsupported for years. Production needs PHP 8.2 or newer.
