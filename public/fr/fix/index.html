Vérification / Que faire avec un PHP ancien

Guide pratique

Mon PHP est ancien — que faire ?

Si votre branche est encore prise en charge, passez à 8.5.12, 8.4.27, 8.3.36 ou 8.2.35. Si vous êtes bloqué sur 8.1, 8.0 ou 7.x, PHP amont n’a pas de version pour vous — mais les paquets deb.sury.org contiennent le rétroportage, et Ubuntu 22.04 a corrigé php8.1 par une mise à jour normale. Vérifiez d’abord la version du paquet : le correctif est peut-être déjà installé.

Faits vérifiés auprès des sources primaires le 23 octobre 2026.

Vérifier le serveur

Réponse courte

Mettez PHP à jour vers la version corrigée de votre branche. Si la mise à jour est impossible, installez un paquet rétroporté du dépôt de votre distribution ou de deb.sury.org. Désactiver les contrôles de sécurité et ajouter des PPA au hasard ne résout pas le problème.

Les branches 8.2–8.5 reçoivent des versions officielles de PHP. Il n’y a pas de version officielle pour 8.1, 8.0, 7.x et 5.x, mais les distributions et Sury publient des rétroportages. Ci-dessous : comment vérifier ce qui est installé et quoi faire dans chaque cas.

Scénario 1. PHP peut être mis à jour

C’est la meilleure voie : une version officielle contient tous les correctifs de la branche, pas seulement celui de ces deux CVE.

  1. Identifiez la branche et la version exacte : php -v et php-fpm -v. Si les commandes manquent, cherchez la version dans le panneau d’hébergement.
  2. Mettez à jour les paquets de la distribution : sudo apt update && sudo apt upgrade sous Debian/Ubuntu ou sudo dnf upgrade sous RHEL.
  3. Redémarrez PHP-FPM et le serveur web : sudo systemctl restart php8.3-fpm. Sans redémarrage, certains workers gardent l’ancien code.
  4. Vérifiez que php -v affiche 8.5.12, 8.4.27, 8.3.36 ou 8.2.35 pour votre branche, ou plus récent.
php -v
php-fpm -v

sudo apt update
sudo apt upgrade

sudo systemctl restart php8.3-fpm

dpkg -l | grep php

Ne vous fiez pas seulement à l’en-tête X-Powered-By : sa version peut être antérieure au correctif. Vérifiez le paquet : dpkg -l | grep php sous Debian/Ubuntu ou rpm -q --changelog php-cli | head -40 sous RHEL.

Si apt upgrade ne propose rien, vérifiez que le dépôt de sécurité de la distribution est activé.

Scénario 2. Vous êtes bloqué sur 8.1, 8.0 ou 7.x

Il n’y a pas de version officielle de PHP pour ces branches. Le correctif peut venir d’un paquet de la distribution ou du dépôt tiers Sury. Sury n’est pas le canal de sécurité officiel de Debian/Ubuntu : vérifiez d’abord si votre distribution propose déjà le correctif.

Vérifiez d’abord le dépôt de votre distribution

Sury est un dépôt tiers, pas un canal de sécurité officiel. Faites un instantané ou une sauvegarde, testez la mise à jour sur un environnement de recette et n’ajoutez pas de PPA au hasard.

Comment ajouter le dépôt Sury

Installez la clé et ajoutez le dépôt avec les commandes du README officiel Sury :

sudo apt-get update
sudo apt-get -y install lsb-release ca-certificates curl
sudo curl -sSLo /tmp/debsuryorg-archive-keyring.deb https://packages.sury.org/debsuryorg-archive-keyring.deb
sudo dpkg -i /tmp/debsuryorg-archive-keyring.deb
sudo sh -c 'echo "deb [signed-by=/usr/share/keyrings/debsuryorg-archive-keyring.gpg] https://packages.sury.org/php/ $(lsb_release -sc) main" > /etc/apt/sources.list.d/php.list'
sudo apt-get update

Mettez à jour uniquement les paquets de votre branche. Exemple pour PHP 8.1 :

sudo apt-get install --only-upgrade php8.1-cli php8.1-fpm php8.1-common

Remplacez 8.1 par 8.0, 7.4 ou une autre branche. --only-upgrade met à jour les paquets déjà installés et n’ajoute pas d’extensions inutiles.

Vérifiez les versions de PHP, FPM et du paquet :

php -v
php-fpm8.1 -v
dpkg -l | grep '^ii  php8.1'

Redémarrez FPM et le serveur web :

sudo systemctl restart php8.1-fpm
sudo systemctl restart apache2

Pour nginx, redémarrez nginx. Si le serveur héberge plusieurs versions de PHP, redémarrez le service et le pool de la branche concernée.

Scénario 3. Hébergement managé ou pas d’accès root

C’est l’hébergeur qui effectue la mise à jour. Demandez au support de confirmer la version du paquet, pas seulement celle du panneau.

Ce qu’il faut vérifier dans le panneau

  • La disponibilité de PHP 8.2, 8.3, 8.4 ou 8.5.
  • La date de la dernière mise à jour de PHP et l’existence d’un rétroportage pour votre branche.
  • Le redémarrage des workers PHP-FPM après un changement de version.
  • La possibilité de lancer une copie de recette et de tester le site avant le basculement.

Modèle de message au support

Bonjour,

Mon hébergement utilise PHP [version]. Pouvez-vous confirmer que CVE-2026-109618 et CVE-2026-109619 sont corrigées dans le paquet PHP installé ?

Si la version corrigée n’est pas disponible, pouvez-vous basculer le site sur PHP 8.2 ou plus récent, ou installer un paquet rétroporté ? Sinon, quelles mesures temporaires prenez-vous en charge ?

Merci de m’envoyer la sortie de php -v et la version du paquet (dpkg -l | grep php ou rpm -q php-cli), ainsi que la date de la dernière mise à jour de PHP.

Merci.

N’envoyez pas de mots de passe, de jetons ni de données clients. La version de PHP, le nom de l’offre et la sortie de php -v suffisent.

Si l’hébergeur ne peut pas mettre PHP à jour, la seule voie fiable est de déplacer le site vers une plateforme avec une version prise en charge.

Scénario 4. Vérifiez à nouveau le résultat

Après la mise à jour et le redémarrage, revenez à la page principale et relancez la vérification passive. Elle affiche la version de PHP divulguée, mais ne prouve pas que le correctif est installé : le verdict reste une estimation du risque.

Ouvrir la vérification

Pour l’automatisation : POST /api/check avec le corps {"url":"https://example.com","lang":"fr"}. L’API est décrite dans llms-full.txt.

Liste de contrôle après la mise à jour

  • php -v et php-fpm -v affichent la nouvelle version.
  • dpkg -l | grep php (ou rpm -q php-cli) affiche le paquet corrigé.
  • Le service PHP-FPM et le serveur web ont été redémarrés.
  • La nouvelle vérification n’affiche ni vulnerable ni likely_vulnerable.

Ce qu’il ne faut PAS faire

  • Ne désactivez pas les contrôles de sécurité, le WAF, open_basedir ou d’autres protections pour rester compatible avec du vieux code. Cela augmente le risque sans corriger la CVE.
  • N’installez pas PHP depuis des PPA au hasard ou des compilations trouvées sur un forum : vous ne pouvez pas vérifier que le paquet contient le correctif.
  • Ne croyez pas qu’un changement de version dans le panneau redémarre tous les workers. Vérifiez php -v et redémarrez FPM.
  • Ne laissez pas phpinfo ni les pages de diagnostic accessibles avant l’installation de la mise à jour.
  • Ne repoussez pas la sortie de 5.x et 7.x : le rétroportage corrige ces deux CVE mais ne rend pas la branche prise en charge.

Questions fréquentes sur PHP ancien

Mon PHP est en 8.1. N’y a-t-il vraiment pas de correctif officiel ?

Oui, il n’y a pas de version amont de PHP pour 8.1. Mais Ubuntu 22.04 et Sury ont publié des paquets rétroportés : vérifiez la version du paquet, pas seulement celle de PHP.

Puis-je simplement passer à PHP 8.5 ?

Oui, si l’application est compatible. 8.5 est la branche la plus récente, mais testez d’abord les extensions et le site sur un environnement de recette.

deb.sury.org est-il sûr ?

C’est un dépôt tiers populaire, mais pas le canal de sécurité officiel de Debian/Ubuntu. Ajoutez-le uniquement depuis le README officiel, avec une sauvegarde et une vérification du changelog.

Comment savoir si le correctif est déjà installé ?

Vérifiez la version du paquet et le changelog : dpkg -l | grep php et apt-get changelog php8.1. La version de l’en-tête X-Powered-By peut être ancienne.

Faut-il redémarrer le serveur après la mise à jour ?

Oui. Redémarrez PHP-FPM et le serveur web, sinon certains workers gardent l’ancien code.

La vérification fonctionne-t-elle si PHP est masqué ?

Non. Le verdict sera unknown : vérifiez la version sur le serveur avec php -v.

Que faire si mon hébergeur ne met pas PHP à jour ?

Envoyez le modèle ci-dessus et demandez la version du paquet. S’il n’y a pas de correctif, déplacez le site vers une plateforme avec PHP 8.2 ou plus récent.

Les mesures temporaires suffisent-elles ?

Elles réduisent le risque mais ne remplacent pas le correctif. Désactiver session.upload_progress et limiter les requêtes ne corrigent pas complètement la CVE.

Cela s’applique-t-il à PHP 5.6 ?

Sury a aussi reconstruit 5.6 avec le rétroportage, mais la branche n’est plus prise en charge depuis longtemps. La production exige PHP 8.2 ou plus récent.
